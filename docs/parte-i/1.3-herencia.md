# Parte I — Actividad 1.3: herencia JOINED en el demo

Clases analizadas: `PersonRecord`, `StudentRecord` e `InstructorRecord` (`infrastructure.jpa.record`).

```java
@Entity @Table(name = "people")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class PersonRecord {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
    @Column(nullable = false) private String fullName;
    @Column(nullable = false, unique = true) private String email;
}

@Entity @Table(name = "students")
public class StudentRecord extends PersonRecord {
    @Column(nullable = false, unique = true) private String studentNumber;
    @ManyToMany @JoinTable(name = "student_courses", ...) private Set<CourseRecord> courses;
}

@Entity @Table(name = "instructors")
public class InstructorRecord extends PersonRecord {
    private String office;
}
```

## 1. ¿Qué hace `@Inheritance(strategy = InheritanceType.JOINED)`?

Le indica a JPA que la jerarquía se guarda con **una tabla por clase**, unidas por la clave primaria:

- La raíz (`PersonRecord`) tiene la tabla `people` con los atributos comunes y la generación del id.
- Cada subclase concreta tiene su propia tabla (`students`, `instructors`) solo con sus atributos. Su PK (`id`) es a la vez **FK hacia `people.id`**.
- **Al guardar** un `StudentRecord`, Hibernate hace dos `INSERT`: primero en `people` (que genera el id) y luego en `students` con ese mismo id.
- **Al leer** un estudiante hace un `INNER JOIN people ↔ students`. En una consulta polimórfica (todas las `PersonRecord`) usa `LEFT OUTER JOIN` con todas las subtablas y un `CASE` para saber qué subclase instanciar. Por eso **no hace falta columna discriminadora**.
- La clase raíz es `abstract`, así que no puede existir una persona que no sea estudiante ni instructor. Aun así, la BD lo permitiría si se inserta a mano solo en `people`.

DDL que generó Hibernate al ejecutar el demo:

```sql
create table people (id bigint generated by default as identity, email varchar(255) not null unique,
                     full_name varchar(255) not null, primary key (id));
create table students (id bigint not null, student_number varchar(255) not null unique, primary key (id));
create table instructors (id bigint not null, office varchar(255), primary key (id));
alter table students    add constraint FK... foreign key (id) references people;
alter table instructors add constraint FK... foreign key (id) references people;
```

## 2. ¿Qué atributos van en la tabla base y cuáles en las especializadas?

| Tabla | Columnas | Origen |
|---|---|---|
| `people` (base) | `id` (PK, identity), `full_name` (NOT NULL), `email` (NOT NULL, UNIQUE) | Atributos de `PersonRecord`, comunes a todas las personas |
| `students` | `id` (PK + FK → `people.id`), `student_number` (NOT NULL, UNIQUE) | Atributos propios de `StudentRecord` |
| `instructors` | `id` (PK + FK → `people.id`), `office` (nullable) | Atributo propio de `InstructorRecord` |
| `student_courses` | `student_id` (FK → **`students.id`**), `course_id` | El muchos a muchos se declara en `StudentRecord`, así que su FK apunta a la subtabla y no a `people` |

Ventaja de JOINED: las restricciones del subtipo se pueden declarar en la BD. `student_number` es `NOT NULL` solo para estudiantes, cosa que no sería posible en una tabla única.

## 3. Clases de dominio vs. clases JPA de la jerarquía

| Aspecto | Dominio (`Person`, `Student`, `Instructor`) | JPA (`PersonRecord`, `StudentRecord`, `InstructorRecord`) |
|---|---|---|
| Paquete | `domain` | `infrastructure.jpa.record` |
| Anotaciones | Ninguna: Java plano | `@Entity`, `@Table`, `@Inheritance`, `@Id`, `@Column`, `@ManyToMany`… |
| Propósito | Representar el concepto de negocio | Representar cómo se guarda en tablas |
| Jerarquía | `Person` abstracta, con `Student` e `Instructor` como subclases | Paralela: `PersonRecord` abstracta, con `StudentRecord` e `InstructorRecord` |
| Matrículas | `Student.courseIds`: `List<Long>` (solo ids, sin entidades) | `StudentRecord.courses`: `Set<CourseRecord>` (entidades administradas, LAZY) |
| Identidad | `id` con `setId` público para asignarlo después de guardar | `id` generado por la BD (`IDENTITY`), sin setter |
| Constructores | Vacío público y completo | Vacío `protected` (exigido por JPA) y uno con datos, sin `id` |
| Decisiones de almacenamiento | No conoce tablas, joins ni estrategia de herencia | Decide nombres de tabla, `NOT NULL`, `UNIQUE` y la estrategia `JOINED` |
| Conversión | — | `DomainMapper` traduce entre ambas (por ejemplo, `courses` → `courseIds`) |

Las dos jerarquías coinciden en forma, pero son **independientes**. Si mañana se usara `SINGLE_TABLE`, solo cambiarían las anotaciones de los Records; el dominio seguiría igual. A la inversa, el dominio podría reorganizar su jerarquía (por ejemplo, con composición en vez de herencia) mientras el mapeador siga produciendo los mismos Records.

En el demo, el mapeador no incluye `Instructor` ↔ `InstructorRecord` y no hay repositorio de instructores. La subclase existe para mostrar la herencia en el esquema, pero no se usa en la API.

## 4. ¿Qué cambiaría con `SINGLE_TABLE` o `TABLE_PER_CLASS`?

### `SINGLE_TABLE`

```sql
create table people (
    dtype          varchar(31) not null,   -- discriminador: 'StudentRecord' / 'InstructorRecord'
    id             bigint generated by default as identity primary key,
    full_name      varchar(255) not null,
    email          varchar(255) not null unique,
    student_number varchar(255) unique,     -- ya no puede ser NOT NULL
    office         varchar(255)
);
```

- **Una sola tabla** para toda la jerarquía, con una **columna discriminadora** (`dtype`, configurable con `@DiscriminatorColumn` y `@DiscriminatorValue`).
- Lecturas y escrituras **sin joins**: es la estrategia más rápida y las consultas polimórficas son triviales.
- Las columnas propias de cada subtipo deben ser **nullable**, porque un instructor no tiene `student_number`. Se pierde la restricción `NOT NULL` en la BD; habría que reponerla con un `CHECK` o validarla solo en la aplicación.
- La tabla se vuelve dispersa (muchos `NULL`) a medida que se agregan subtipos.
- `student_courses.student_id` apuntaría a `people.id`, así que la BD no podría garantizar que el matriculado sea un estudiante.

### `TABLE_PER_CLASS`

```sql
create table students    (id bigint primary key, full_name varchar(255) not null, email varchar(255) not null unique,
                          student_number varchar(255) not null unique);
create table instructors (id bigint primary key, full_name varchar(255) not null, email varchar(255) not null unique,
                          office varchar(255));
-- no existe tabla "people" (la raíz es abstracta)
```

- **Una tabla completa por cada clase concreta**, con las columnas heredadas repetidas. No hay tabla base ni joins para leer un subtipo concreto.
- Las consultas **polimórficas** (`SELECT p FROM PersonRecord p`) requieren `UNION ALL` entre todas las tablas, lo cual es costoso.
- `GenerationType.IDENTITY` **no está permitido**: los ids deben ser únicos en toda la jerarquía. Habría que cambiar a `SEQUENCE` o `TABLE`.
- La unicidad de `email` ya no es global: el mismo correo podría estar en `students` y en `instructors`.
- No se puede declarar una FK hacia "cualquier persona", porque no hay tabla común.

### Resumen

| Criterio | JOINED (actual) | SINGLE_TABLE | TABLE_PER_CLASS |
|---|---|---|---|
| Tablas | 1 base + 1 por subtipo | 1 | 1 por clase concreta |
| Joins al leer | Sí | No | No (subtipo) / `UNION` (polimórfica) |
| `NOT NULL` por subtipo | Sí | No | Sí |
| Columna discriminadora | No | Sí | No |
| Normalización | Alta | Baja (columnas nulas) | Media (columnas repetidas) |
| `IDENTITY` | Sí | Sí | No |
| Unicidad global de `email` | Sí | Sí | No |

Para el demo, `JOINED` es la opción más adecuada: los subtipos tienen atributos distintos con restricciones propias, y la integridad referencial (`student_courses` → `students`) se puede expresar en la base de datos.
